# Bedrock Spine — the binding spec

This document is the spine: every worker builds against it; deviations are
defects. Donor material in `spec/donor-*` is evidence, never law. `spec/floor-v2.md`
is the floor content (§4 invariants + breadcrumbs are the seed's substance).

## 1. What bedrock is

A single Rust binary, `bedrock`, published as crate `yeetz-bedrock` (name
`bedrock` is squatted). It is a tool, not a skill: its instructions ship
compiled into it and are emitted as output. Three commands plus two internal:

- `bedrock init` — seed a NEW repo: install `situation/` skeleton + seed floor
  vertices + workflow; generate root `AGENTS.md`; print the init instruction
  set (§7) to stdout for the invoking agent to action.
- `bedrock adopt` — epoch-change an EXISTING repo: same install, plus write an
  epoch record vertex (§6) declaring the cut line; print the adopt instruction
  set (§7).
- `bedrock help` — the contract, short.
- `bedrock check` — validate `situation/` (§4). CI entrypoint; also run by
  init/adopt before finishing.
- `bedrock build` — compile root `AGENTS.md`, the resident TriG working-set
  projection (§5). Fails if `check` fails.

Version gate: once published, the binary checks crates.io for the latest
version at startup of `init`/`adopt` (never `check`/`build` — CI must not
depend on the network); if stale it refuses and prints the update command.
`--offline` runs anyway but stamps the version into whatever record it writes.
Until first publication the gate is a no-op with a notice.

## 2. Repository layout (this repo)

```
Cargo.toml          # the crate: yeetz-bedrock, binary name bedrock
src/                # the compiler + CLI
seed/               # what init/adopt installs (situation skeleton, workflow template)
situation/          # bedrock's own instance — the tool eats its own output
spec/               # this spine + donors (never installed into consumers)
tests/              # golden fixtures + CLI behavior tests
README.md           # human/crates.io-facing; carries no agent law
AGENTS.md           # GENERATED by bedrock build from situation/ — never hand-edited
```

## 3. The situation structure (installed in every consumer repo)

```
situation/
  definition/      # resident invariants, breadcrumbs, terms
  architecture/    # resident current structure and intent
  risk/            # resident present-tense warnings; deleted when retired
  plan/            # full execution Plans; only active routing faces resident
  record/          # Decisions resident; epoch/deploy/reflect records cold
  references/      # cold depth docs pointed at by resident vertices

Law: these six directories only; no new top-level directories under
`situation/`; vertices are flat files directly in their namespace directory
(`situation/<ns>/<local-name>.yamlld`); only `references/` may nest freely and
may contain non-YAML-LD files. Exactly ONE `AGENTS.md` per repository, at
root, generated. `README.md` at root only.

## 4. Vertex grammar and check rules

Source files are YAML-LD: YAML 1.2 documents that map to JSON-LD 1.1 under
the constrained profile below. `situation/` is the complete canonical store
and every source is parsed, expanded, schema-validated, and edge-validated.
AGENTS.md is the resident projection (§5), not the historical archive.
`body`, a literal block scalar of unbounded free-form prose, never compiles.
Plan execution payload remains structured and validated but only its active
routing face projects. `bedrock check` enforces, in order:

C1. Placement: every `situation/` file matches §3; any `AGENTS.md` outside
    repo root → FAIL; hand-edit drift of root AGENTS.md (differs from
    regenerated output) → FAIL.
C2. YAML: parses as YAML 1.2; **anchors, aliases, and merge keys are
    forbidden**; comments are allowed and preserved-irrelevant (they do not
    survive to TriG).
C3. LD profile: one `@context` — either the embedded repo-local context or
    the exact IRI of the bedrock context shipped in `seed/`; **no remote
    context loading ever** (oxjsonld default refusal stays on); `@id` and
    `@type` absolute IRIs; **no blank nodes**; named graph membership only
    from the namespace directory (definition|architecture|risk|plan|record).
C4. Schema: each namespace has a JSON Schema in `seed/schemas/`; every vertex
    validates against its namespace schema (jsonschema crate). Minimum vertex:
    `@id`, `@type`, `label` or one-line description, ≥0 typed edges, optional
    `source` pointer into `references/` or repo paths, optional uncompiled
    `body`. Every Plan declares `disposition.state`:
    draft|active|done|abandoned.
C5. Source references: every edge target resolves — to another source vertex
    `@id` or an existing repo path. Dangling → FAIL.
C6. Determinism: `build` output is byte-stable — same input, same bytes.
C7. Parse-back: emitted TriG re-parses (oxttl) to a dataset equal to the
    resident projection; inequality → FAIL.
C11. Projection closure: a resident vertex may not point by vertex IRI at a
     cold source. Use a path pointer for history or promote the target into
     resident knowledge; the injected graph never exposes a dangling edge.

Advisory (never failing): `check` and `build` print the projection report —
exact AGENTS.md bytes; source/resident counts; active versus cold plan states;
resident Decisions versus episodic records; and a SOFT line per resident face
over 4096 chars (≈1k tokens; target 500–1000). Soft is soft: PR guidance,
never an exit-code change.

Failure output: one violation per line, `RULE path:line message`, exit 1.
Brittleness with intent: loud, exact, agent-fixable.

## 5. Compile pipeline (locked stack)

```
YAML (serde_norway, exact-pinned) → serde_json::Value
  → `body` stripped
  → oxjsonld (JSON-LD 1.1, remote loading disabled) → full source Quads
  → source schema + edge validation
  → deterministic resident projection:
      definition/architecture/risk → full compact face
      plan active → routing allowlist + state + document edge
      plan draft/done/abandoned → cold
      record Decision → resident; Epoch/Deploy/Reflect → cold
      references → cold
  → C11 resident-edge closure
  → deterministic sort → oxttl TriGSerializer
  → AGENTS.md (comment preamble + resident TriG)
  → parse-back equivalence on the emitted file itself
  → advisory projection report
```

Exact pins in Cargo.toml (`=x.y.z`). Golden tests: fixtures in
`spec/donor-fixtures/` and `spec/donor-execution-record.yamlld` must compile;
every C1–C11 rule has direct contract coverage; fixture-based rules keep both polarity.

AGENTS.md (generated — THE single artifact):
1. A `#`-comment preamble: machine stamp; the resident/cold how-to-read;
   identity title; operating lines (verbs, authoring loop, THE CHAIN, Plan
   lifecycle, Decisions, base-protocol pointer); digest marker.
2. The complete resident TriG projection. The whole file is valid TriG, so
   C7 reads the exact file agents receive: delivery is guaranteed, never
   optional.

Residency:
- definition, architecture, current risks: resident faces;
- Plan `active`: only @type, label, intent, routing edges, synthesized state,
  and automatic document pointer resident; acceptanceCriteria, tasks,
  witnesses, reflectDepth, residual, statement, and body stay cold;
- Plan draft/done/abandoned: entirely cold;
- Decision: resident (the complete supersession chain stays walkable);
- EpochRecord, DeployRecord, ReflectVerdict, references: cold.

There is no separate graph file and no prose projection. Every resident
vertex carries an automatic `document` edge to its source. Cold source stays
discoverable through the SituationStructure paths without enumeration.
Editing only cold content changes no artifact bytes.

## 6. Epoch record (adopt)

`situation/record/epoch-<utc-date>-<short-sha>.yamlld`: a vertex typed
EpochRecord carrying: the commit SHA of the cut, bedrock version (and
`--offline` stamp when used), a one-line statement: everything after this
commit operates under bedrock; prior history is reference, never law. `init`
writes the same record with `mode: init` as the repo's first record.

## 7. Instruction sets (compiled into the binary, emitted on success)

Two texts, authored in `src/instructions/` as markdown constants, emitted to
stdout after init/adopt completes. Content requirements — init: what was
installed; the six namespaces and what belongs in each; the five verbs
(think/plan/execute/reflect/deploy) as branch prefixes with one line each; the
one-AGENTS.md law; how to add a vertex and run `bedrock build`; commit and
open a PR — a human merges. Adopt: all of the above, plus: the epoch record
written and what it means; prior AGENTS.md content is donor material — convert
what the repo still relies on into vertices forward-only, never by sweep;
nested AGENTS.md files found in the tree are listed and must be deleted (their
surviving law becomes vertices). Tone: terse imperative, no ceremony, ≤60
lines each.

## 8. Worker boundaries

Four workers, each on its own branch/worktree, each owning disjoint paths:

- W1 compiler: `Cargo.toml`, `src/`, `tests/` (rules C1–C7, pipeline, CLI,
  goldens). Does NOT author seed content or vertices.
- W2 floor vertices: `situation/definition/*.yamlld` from
  `spec/floor-v2.md` §4 (16 invariants, tagged `layer: floor`) + breadcrumb
  vertices + bedrock's own identity/architecture vertex; also
  `seed/schemas/*.json` (the namespace JSON Schemas) and the repo-local
  `@context` in `seed/context.yamlld`. Grammar per §4.
- W3 seed + workflow: `seed/` skeleton (situation dirs with .gitkeep,
  workflow template calling `bedrock check` + `build` on `situation/**`
  changes, README stanza template) — installable by copy; plus
  `situation/references/review-playbook.md` and `spike-playbook.md` distilled
  from the two donor files (playbooks: stages, evidence rules, gates — ≤120
  lines each, no Sol/Terra names, no lane vocabulary).
- W4 README + instruction sets: `README.md` (crates.io-ready: what bedrock
  is, install, the three commands, the model in ~80 lines) and
  `src/instructions/init.md` + `adopt.md` per §7 (W1 wires them in with
  `include_str!`).

No worker edits `spec/`. No worker pushes `main`. Every worker runs
`cargo fmt` on touched Rust and leaves the tree building (`cargo check`)
where its ownership allows; W2–W4 do not run cargo at all.
